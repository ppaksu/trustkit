# 검증 가능한 거절 기록 로그

TRUST404 해커톤 · 트랙 3 Off-chain Rejection Records

체인에는 제출된 트랜잭션만 남는다. 지갑·커스터디·컴플라이언스 계층에서 실행 전에 거절된 요청은
온체인 흔적이 없다. 그래서 막은 쪽은 차단 실적을 입증할 수 없고, 막힌 쪽은 부당한 차단을
반박할 증거가 없다. 이 프로젝트는 거절 기록에 append-only 로그와 온체인 앵커를 붙인다.

보안 도구를 위한 로그가 아니라, 보안 도구를 감시하는 로그다.

## 위협 모델

### 공격자

| ID | 공격자 | 능력 | 동기 |
|---|---|---|---|
| A1 | 부정직한 게이트키퍼 | 영수증 발급 가능, 로그 제출 생략 가능 | 검열 은폐, 책임 회피 |
| A2 | 부정직한 로그 운영자 | 로그 저장소 전체 통제 | 불리한 기록 삭제, 감사자별 다른 뷰 제공 |
| A3 | 외부 위조자 | 네트워크 관측, 임의 데이터 제출 | 허위 거절 기록 생성 |
| A4 | 호기심 있는 관찰자 | 공개 로그 전체 열람 | 타인의 거래 패턴 프로파일링 |

세 가지 공격 시나리오로 각각을 실증한다. 게이트키퍼가 거절 사실을 부인하는 경우(A1),
접수만 하고 트리에 넣지 않는 경우(A1+A2), 과거 리프를 고치고 재앵커하는 경우(A2).
셋이 서로 다른 장치에 걸린다. 순서대로 서명 복원, 포함 증명 부재, 일관성 증명 실패다.

### 신뢰 가정

- 앵커 컨트랙트가 배포된 체인은 정직하다.
- 게이트키퍼와 로그 운영자의 서명키는 유출되지 않았다.
- 요청자는 자신의 영수증과 salt 를 보관한다. 분실하면 증명이 불가능하다.
- 게이트키퍼 레지스트리의 소유자는 정직하다. 운영 환경에서는 다중서명이 필요하다.
- 검증자는 앵커 트랜잭션이 충분히 확정된 뒤 검증한다.

## 보장 경계

무엇을 증명하지 **않는지**를 먼저 밝힌다. 과장된 주장은 이 부류 시스템의 흔한 실패다.

**증명한다**

- 영수증의 진위. EIP-712 서명이 온체인 레지스트리에 등록된 게이트키퍼 주소로 복원된다.
- 로그 포함 여부. 온체인에 앵커된 루트에 대한 inclusion proof 로 확인한다.
- 이력의 불변성. 두 앵커 사이의 consistency proof 로 과거 수정을 검출한다.
- 커밋된 필드 집합. `keys` 배열이 서명에 묶여 있어 필드 누락이 드러난다.

**증명하지 않는다**

- 영수증이 발급되지 않은 요청의 존재. 게이트키퍼가 응답 자체를 하지 않으면 요청자에게
  아무 증거가 없다. 완전한 non-omission 은 이 구조로 풀리지 않으며, 요청자가 응답을
  받았다는 사실을 증명하는 별도 계층이 필요하다.
- 거절 판단의 정당성. 판단이 있었다는 사실만 기록한다. 부당한 차단이 자동으로 판정되지는
  않으나, 기록이 남는 것 자체가 사후 이의 제기의 전제가 된다.
- 수학적 non-membership. 누락 검출은 서명된 접수 확인의 약속 시각이 지났는데 포함 증명이
  없다는 운영 책임성 신호다. sparse/sorted Merkle tree 를 쓰지 않으므로 암호학적 부재 증명이
  아니다.
- 커밋된 값이 실제 요청과 일치하는지. `keys` 는 어떤 필드를 커밋했는지만 묶는다.

### 알려진 제약

- 발급 시각이 평문이라 시각 메타데이터가 노출된다.
- 게이트키퍼 주소, 정책 해시, 트리 크기 변화가 공개된다.
- 해시와 서명 알고리즘이 SHA-256 과 secp256k1 로 고정이다. RFC 9162 가 도입한 알고리즘
  민첩성을 따르지 않았다.
- 단일 로그 운영자와 파일 기반 저장소는 데모 구성이다.

## 실행

```bash
npm install
node --test "test/**/*.test.ts"
```

테스트 88종. 머클 로그 자료구조, 레코드 계층, 서명 계층, 로그 저장소, HTTP 계층.

머클 부분 7종은 RFC 6962 §2.1 정의를 구현하고, 반복형 검증기로 교차 확인한다.
음성 테스트 세 개가 포함되어 있다. 리프를 고쳤을 때 일관성 증명이 반드시 실패하는지,
audit path 를 변조했을 때 포함 증명이 실패하는지, 다른 인덱스로 주장했을 때 실패하는지.

레코드 계층 24종은 RFC 8785 정규화와 필드 커밋의 위치 결합을 확인한다. 게이트키퍼가
한 키를 두 번 커밋해 다른 키를 빠뜨린 경우가 드러나는지도 포함한다.

서명 계층 16종은 EIP-712 도메인 분리를 확인한다. 체인 식별자나 검증 컨트랙트가 다르면
서명이 재사용되지 않는지, 두 서명 타입이 서로 섞이지 않는지.

로그 계층 21종은 접수 검증 일곱 항목과 증명 발급을 확인한다. 위조 요청에 온체인 조회가
나가지 않는지, 서버가 리프를 덮는 가장 이른 앵커를 고르는지, 과거 리프를 직접 고쳤을 때
일관성 증명이 깨지는지.

앵커 컨트랙트.

```bash
cd contracts && forge test -vv
```

불변식 9종. 운영자 아닌 주소의 앵커 거부, `treeSize` 단조 증가 강제, 고정된 루트의 불변성,
영 루트 거부, `treeSize` 로 루트 조회, 소유자와 운영자 권한 분리.

앵커 1회 비용은 트랜잭션 전체 기준 50,984 가스다. 이 중 컨트랙트 실행분이 24,964 이고
나머지는 기본료와 calldata 다. 거절 건당이 아니라 앵커 1회당이므로, 한 번의 앵커가 덮는
기록 수만큼 분모가 커진다.

온체인 앵커, 포함 증명, 일관성 증명, 선택적 공개까지 16단계를 한 번에 지나간다.
마지막 검증은 로그 서버의 응답을 믿지 않고 체인에서 루트를 다시 읽어 대조한다.

명세 대조. 실제로 생성된 거절 기록 하나를 명세 4장의 정의와 맞춰 본다.

```bash
npm run inspect
```

각 항목을 라이브러리 함수를 다시 부르지 않고 손수 재계산해서 비교한다. 구현이 자기
자신과 일치하는지가 아니라 문서에 적힌 정의와 일치하는지를 확인한다. 33항목.

## 공격 시연

세 공격이 각각 다른 장치에 걸린다. 순서대로 보면 구조가 설명된다.

```bash
npm run attack:d1   # 게이트키퍼가 부인 → 검증 2단계, 서명 복원
npm run attack:d2   # 로그가 접수만 하고 누락 → 검증 5단계, 포함 증명 부재
npm run attack:d3   # 과거 기록 수정 후 재앵커 → 검증 6단계, 일관성 증명 실패
```

세 번째가 기술적 하이라이트다. 서명만 있는 로그는 이 공격을 막지 못한다.
두 번째는 운영 책임성 신호이지 수학적 non-membership 증명이 아니며, 약속 시각
전후로 판정이 달라지는 것까지 시연에 들어 있다.

## 표준

머클 트리는 RFC 6962 를 그대로 따른다. RFC 9162 가 표준 계층에서 이를 대체했으나
트리 정의를 변경 없이 승계했으므로 구현부는 두 판본이 동일하다.
9162 가 바꾼 것은 사전인증서 형식, TLS 확장, 로그 식별 OID 등 인증서 생태계 배관이라
거절 기록 로그에는 적용되지 않는다. 대조할 참조 구현과 테스트 벡터도 6962 쪽에 있다.

JSON 정규화는 RFC 8785 JCS, 서명은 EIP-712 를 사용한다.
